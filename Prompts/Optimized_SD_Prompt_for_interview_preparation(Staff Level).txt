
Think of it as producing an interview playbook, not a design specification.
The prompt should generate something you can realistically review in 30–45 minutes before an interview.

This produces a study guide that's comprehensive enough for a Staff/Principal interview while 
remaining practical to review and use during preparation. It emphasizes the discussions interviewers 
actually have rather than generating a specification document.





# Staff Software Engineer System Design Interview Prompt

Act as a Principal/Staff Software Engineer preparing for a 30–45 minute system design interview.

Design the following distributed system:

# <SYSTEM NAME>

---

# Goal

Produce a concise, interview-ready study guide that covers everything expected in a Staff Software Engineer system design interview.

The output should read like the notes of an experienced engineer preparing for an interview—not a design document or textbook.

Optimize for:
- interview discussion
- engineering reasoning
- trade-offs
- communication

Avoid unnecessary implementation details.

Focus on the important architectural decisions.

---

# Writing Style

Write like a senior engineer preparing another senior engineer.

Prefer depth over breadth.

Avoid textbook explanations.

Keep every section concise.

Avoid repeating information.

Only include components that genuinely belong in this system.

Every explanation should answer:

- Why does this component exist?
- What happens if it fails?
- How does it scale?
- What trade-offs does it introduce?

Use Markdown.

Use Mermaid flowchart LR.

Keep diagrams readable.

Optimize the entire output so it can realistically be reviewed in 30–45 minutes before an interview.
